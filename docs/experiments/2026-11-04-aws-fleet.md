## Question

Four engineer sessions shared one 14-core Mac all day, each pool defaulting to 10 workers, at a load average of
50–200; every long run went at a quarter of its idle speed. Can a fleet of AWS boxes, one per job, bring the long jobs
to at most a quarter of their recorded wall time, with results identical to the Mac's? Before building it: which way
of readying a box is fastest (custom image, container, snapshot volume, warm pool, or a stock image with user data)?

## How a box is readied: measured in us-west-2

Seven trial boxes, 15:23–15:36 UTC, about $0.35, all terminated with the trial image and its snapshot deleted. The
scripts were in a scratch folder that the Mac's reboot cleared; their timings are below. "Submit" is the call to
`run-instances` on the Mac.

| Step | Time |
|---|---|
| submit → user data starts, stock Ubuntu 24.04 (four launches, arm64 and amd64) | 19.1–20.8 s |
| apt ffmpeg / uv install / shallow clone / `uv sync --frozen` cold / first import of the stack | 31 / 1 / 0.8 / 2.1 / 2.9 s |
| S3 → box, 252 objects, 18.4 GB, s5cmd (twice) / AWS CLI with CRT | 6.2, 6.5 s (2.9 GB/s) / 7.8 s |
| 661 small objects, 50 MB, s5cmd | 0.44 s |
| docker.io install / pull python:3.12 (1.62 GB) / first `docker run` | 17 / 8.6 / 4.6 s |
| custom image: bake ≈ 90 s, `create-image` of a 30 GB root | 188 s |
| launch from it: submit → boot script / first import (lazy-loaded root) | 21–25 s / 24.2 s |
| the same with provisioned volume initialization at 300 MiB/s | first import 24.1 s |
| warm restart of a stopped box: start → boot script / import / 8 GiB read from gp3 | 12.2 s / 2.6 s / 546 MB/s |
| one serial test stage (tests/test_phase0_cli.py, jobs = 1): c8g / c7a / the Mac at a load of 22 | 13.7 / 17.2 / 15.4 s |

So a custom image saves about 9 s (its root loads lazily from the snapshot, and initialization doesn't finish
in time to help), a container no more, EBS data volumes load 10–100× slower than S3, AWS Batch and ECS cost
minutes to scale from zero (documentation and third-party measurements), Fargate stops at 32 vCPU, and warm
pools don't take spot instances. The review chose the stock image with user data; with uv, s5cmd and a static ffmpeg
from the bucket a box runs its command about 30 s after submit (157 s submit to done for the Tier 2 case below,
of which 28 s to the supervisor's start and 8 s of preparation).

c8gd.16xlarge spot was refused for capacity twice (us-west-2d, then the whole region), so a job is an EC2 Fleet
over c8g, c8gd, c7g and c7a of one size across a region's AZs, and then across regions (us-west-2, us-west-1,
us-east-2).

## What was built

`tools/aws/` ([README](../../tools/aws/README.md)): the CDK stacks (a private, versioned bucket kept on teardown;
a VPC per region with no inbound rule; a role that reads the bucket and writes, without delete, only jobs/, runs/,
cache-deltas/, data/raw/ and data/derived/; arm64 and amd64 launch templates; a dev box stopped after 30 idle
minutes) and `runs`: launch (shards, resume, inputs from a job's own listing, another checkout), status with
cost, wait, pull, cancel, a real spot interruption, the dev box, and the seed. The branch goes as a git bundle
plus its diff, so a box's run.json records the Mac's commit and dirty flag, plus the instance type, AZ and
market. `parallel.default_jobs` counts physical cores on Linux (hyperthreads on x86, cgroup cpusets).

Checked end to end:
- **Tier 2, Oyster Bay saved-fit** (`runs/2026-11-04-aws-oyster-t2-2/`, c8g.16xlarge spot): 1st of 328, 122.9 m and
  43.3 m, margin 4.9 %, as on the Mac (the margin agrees to the ninth decimal).
- **A spot interruption** sent through Fault Injection Service (`runs/2026-11-04-aws-interrupt-test/`): the
  supervisor saw the notice within 5 s, stopped the command, and had the partial run folder in the bucket two
  minutes before the reclaim time; `runs launch --resume` continued that folder on a fresh box.
- **tools/check.sh on the dev box** (c8g.2xlarge, 8 cores; `runs/2026-11-04-aws-devbox-check/`): 312 passed in
  77 s on uv's CPython 3.12.15 (86 s with the branch sync), against 83 s on the idle Mac; three checks at once, each
  in its own checkout, took 101–103 s each. The first checks on the box failed four tests because every caller
  synced into one shared `~/branch` and runs overwrote each other's tree mid-suite; each `runs dev run` now gets
  its own checkout. Boxes first built their venvs on Ubuntu's Python 3.12.3; they now use the Mac's uv (0.13.7)
  and its managed CPython 3.12.15.
- **The other regions**: a job in us-west-1 (c7g) and us-east-2 (c7a), inputs read across regions from the bucket.

## The reference jobs

Each at the commit of its recorded Mac run, on c8g.16xlarge spot, started together at 16:29 UTC. The Mac numbers
are the records' own, under load.

| Job | Mac | Box | Speed-up | Results |
|---|---|---|---|---|
| warp ranking, 2b4ab86, `full all` then `band all` (runs/2026-11-04-warp/, load not logged) | 4,927 s | 627 s, both modes at once with JOBS = 11 | **7.9×** | `rank_summary` identical, both modes |
| timing-convention sweep, 51f59ce, 45 settings (runs/2026-11-04-timing-convention/, load 13–143) | 8,550 s | 1,945 s, six settings at once with 10 jobs each ([aws_sweep.sh](../../tools/experiments/2026-11-04/aws_sweep.sh)) | **4.4×** | all 45 identical to 3 decimals in rank, pairs, margin and errors |
| cold Tier 1, 6454f67, 11 spans (runs/2026-11-04-bench-6454f67-t1/, load 130) | 3,196 s | 2,059 s | **1.55×** | spans, known point and pooled numbers identical; only timings and their hashes differ |
| cold Tier 1 at dev 9b1b684, `--shard k/11`, one box per shard, merged on the Mac | 3,196 s | 862 s, first launch to merged comparison | **3.7×** | known point identical; spans and pooled differ from 6454f67's as dev's code does (the case version bump, detector changes since) |
| cold Tier 1 at d3a9391, `--shard k/14`, one unit per 4xlarge box (the benchmark study; runs/2026-11-04-tier1-cold-b-s{1..14}of14, merged in runs/2026-11-04-tier1-cold-b-merged, compared in runs/2026-11-04-tier1-cold-compare) | 3,196 s | about 420 s: the longest shard 6 min (units 105–283 s of compute), the comparison 18 s on one box | **≈ 7.6×** | all 11 spans and 6 known-point entries scored; about $0.40 |

The sharded Tier 1 shows what the fleet's limits cost. Its eleven shards took 105–476 s each (the longest,
an eagle-cam span with its known point, on c7a.16xlarge), but four could not start at first (the spot quota,
with A, B and D launching at the same time) and went out a few minutes later on 8xlarge boxes, two of them on
demand in us-east-2; and two c7a.16xlarge boxes in us-east-2 were reclaimed by AWS mid-run (real spot
interruptions, notice at 17:10:35 UTC), uploaded their partial runs and finished on fresh boxes through
`runs launch --resume` in 231 and 266 s. Merging the eleven folders and comparing took 14 s on the Mac. With
capacity free and no interruption, the same shape would take about the longest shard plus boot and merge,
roughly 530 s (6×). The shards cost $0.03–0.19 each, $1.10 in all.

Cold Tier 1 on one box falls short because `bench tier1` at 6454f67 runs its eleven spans one after another and a
span's detect has only 13–45 windows to spread over 64 cores; its spans took 115–223 s each on the box. No idle-Mac
number exists for these runs. Run folders: `runs/2026-11-04-aws-ref-{warp-rank,timing-sweep,tier1-cold}/` and
`runs/2026-11-04-aws-ref-tier1-sharded-*` with the merge in `runs/2026-11-04-aws-ref-tier1-sharded-merge-2/` (the first merge, `-merge/`, ran before the two resumed shards were back and was stopped).

Cost: each reference box was about $0.92–1.05 an hour on spot, so about $0.20, $0.55 and $0.60.

## A provenance gap

The A1/A3 run (jobs `2026-11-04-hypotheses-pairs-s1of8` … `s8of8`) was launched with `runs` from an uncommitted
state of this branch (0cbc405 plus edits, copied into a scratch worktree) before the fleet landed on dev. Its
boxes' run.json records the experiment’s code (the bundle of its pinned checkout), so the results are traceable; what
isn't is the exact `runs` and supervisor that ran them. The original experiment recorded that limitation.

## Regions and transfer

Job boxes run in us-west-2, us-west-1, us-east-2, us-east-1 and eu-central-1, tried in that order; the bucket
stays in us-west-2. A box elsewhere reads its inputs and writes its run folder across regions: $0.02/GB between
US regions and from us-west-2 to Frankfurt, so a few cents for a job's few GB, at seconds rather than
milliseconds of latency (a 29 MB input took 1.4–1.6 s from us-west-1 and us-east-2).

## A stray upload, removed

A failed collect script in the detector study’s session ran `runs launch --input runs/`, which began uploading the Mac's whole
runs/ folder to `data/runs/` in the bucket before it was stopped (no job ran). With the user's go-ahead, 248 of
the 268 folders there were removed at 19:58 UTC: 16,366 objects, 7.56 GB. The 20 kept are the run folders that
job specs read (`--input-run`), 3,087 objects. The bucket is versioned, so every removed object is a delete
marker over a version kept for 30 days; restoring one means deleting its marker. The plan, the removed keys and
the summary are in `runs/2026-11-04-s3-runs-cleanup/`. Since then `--input` refuses runs/ paths and run folders go up
only one at a time through `--input-run`.

The private-mode selftest (`runs/2026-11-04-aws-private-selftest`, run from a throwaway data root with a dummy file)
left a 21-byte `data/private/aws-selftest/note.txt` and its run folder in the bucket; both were removed the same day.

## Check and rehearse before launching

The private pilot’s first three runs failed on the box's environment, not the method: opensky-network.org
unreachable from the boxes, a data path built from the code checkout (`/scratch/dopplertrack/private/...`), and a
`locate/run.json` the code expected in a folder it hadn't made. None shows on the Mac, whose layout and network
differ. `runs launch --check` and `--rehearse` were added for that (README). Replayed as rehearsals on the dev box
with `--resume` (each job's own code, inputs and command): pilot-2's path bug failed the rehearsal after 10 s, the
same `FileNotFoundError`; pilot-3's missing folder after 300 s (361 s on its fleet box), not inside a 4-minute
rehearsal, so the minutes must cover the job's first full stage. The Oyster Bay Tier 2 case rehearsed `ok` to its
2-minute cut-off, 2 min 14 s in all; `--check` took 8 s. The runs: `2026-11-04-rehearse-oyster-t2`,
`2026-11-04-rehearse-seattle-home-pilot` and `-2`, `2026-11-04-rehearse-seattle-home-pilot-3`.

## The seed

The Mac uploads at about 10 MB/s, so only what has no public source went up from it (derived/, the YouTube and
xeno-canto audio, A2O, the seismic windows, aux/, models/ and the caches: about 10 GB). The rest of raw/ came from
its sources on a box (`runs fetch-sources`: adsb.lol from GitHub at 64–80 MB/s per file, the Zenodo datasets at
1–7 MB/s), each file checked against bench/manifest.json's SHA-256 before it went into the bucket.

## Outcome

The fleet works: a box runs a job about 30 s after submit, results match the Mac's, an interruption keeps the
partial run and a resume continues it. The 4× holds where a job spreads over the cores (warp 7.9×, sweep 4.4×) and
not where a driver runs its units one after another (cold Tier 1 at 6454f67, 1.55×); sharding across boxes is the
fix there (cold Tier 1 in 14 shards on 4xlarge boxes, about 7 minutes: 7.6×). The binding limit today is the vCPU quota: 256 spot and 256 on-demand per region (increases requested
in all three regions).
