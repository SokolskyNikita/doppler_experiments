## Question

PLAN Phase 3 step A asks for one command from audio, a date and a box to a verdict, where every failure is an outcome
with a stated reason. Two questions for Tier 2:

1. Does each development case end where it should? The seed cases should end in "ambiguous" with a candidate (step A
   never says "located"), and each failure case in its own reason: flight data ending before the recording, the
   true pair's flights removed, a recording past UTC midnight with one day loaded, a jets-only recording.
2. Which pair rule picks the search events: detect's top two by score (`top2`, the raw-audio profile's rule), or the
   best of all ten pairs of the top five by comparable score (`comparable`)? And what does each cost?

Tier 2 runs every case with the silence filter off, `locate`'s default (S4), and again with it on at the cases' 6 km.

## What `locate` does

`src/dopplertrack/locate.py`, behind `dopplertrack locate AUDIO --date D --bbox ... --out DIR`:

1. **Detect** with the cached detector (60–300 Hz, top 10, 240 s windows). An event is usable when its fit isn't
   weak and its f0 is finite. Fewer than two usable events, or a recording with half its frames or more invalid
   (gaps), end at `no_usable_flyovers`.
2. **Flight data.** No network unless `--fetch` is given; `--traces` takes one file or consecutive days, joined at
   midnight by `adsb.join_days`. Each file's measured envelope must cover the box plus the search range, or the run
   ends at `flight_data_missing_box`. A legacy file without metadata counts only with a declared box
   (`--assume-envelope`), and is then taken as a whole-day cut of the stated date; the record says it was declared.
   The files must cover the stated UTC day to within 600 s (`covered_utc` when a file states one, else its archive
   day), or the run ends at `flight_data_missing_time`.
3. **Search** on the grid with each pair rule. `top2` searches one pair. `comparable` searches every pair of the top
   five with `run_search(comparable=True)` and keeps the pair whose top candidate scores highest. `--pair-rule both`
   runs both and keeps `top2`'s answer, so the two can be compared on one run. Each rule's wall time and top flights
   go in the record's `pair_rules` and the summary.
4. **Clock check.** The top candidate's clock places the recording in UTC. If the recording ends past the loaded
   days, the run ends at `past_utc_midnight` with one day loaded (the reason names `--days 1`), or at
   `flight_data_missing_time` otherwise. No candidate at all ends at `no_surviving_candidate`.
5. **Refine** the winner with the other usable events that `pick_flight` can place.
6. **Verdict**, result record schema v2: `ambiguous`, with `winner_only_refined` and, when the filter is off,
   `silence_filter_off`. The record and its hash are written before anything reads a label.

## Criteria, written before any result

1. **Outcomes.** Each failure case ends in its expected reason code (the comparison's `verdict_as_expected`); the
   negatives and the sources-removed case end in no candidate within 2 km of the truth. A failure case that ends
   elsewhere is a bug in step A's checks, fixed before anything else.
2. **Does the method find the place, given automatic events?** On each seed case, under each pair rule: the rank of
   the true pair among the candidates, and the top candidate's and the refined point's distance from the truth. The
   seed cases count as found when the true pair ranks first and the refined point is within 2 km.
3. **Pair rule.** `comparable` replaces `top2` as locate's default if it finds more seed cases than `top2` and loses
   none that `top2` finds. Otherwise `top2` stays, and comparable's time per case is recorded against it.
4. **Silence filter.** It stays off by default (S4) unless turning it on finds more seed cases and loses none, with
   the negatives still unlocated.

The 2 km is a judgement set here, before any result: above the refinement's 600 m half-width, and well below the tens
of kilometres that separate wrong pairs' candidates in these boxes. The rest are counts.

## Outcome

Against the criteria written before the results:

1. **Outcomes: met except for the midnight case.** The cut-short flight data ends at `flight_data_missing_time`; the
   two negatives, the sources-removed case and Essex put no candidate within 2 km of the truth (the nearest is 43 km
   off). `eagle-cam-midnight-days0` misses `past_utc_midnight` with the filter off and on: its clock comes from a
   wrong pair, so the recording lands at another hour and the midnight check never sees it. That is not a bug in the
   check, so nothing in step A's checks is changed; it is the same failure as the eagle cam's below.
2. **Found from automatic events: Oyster Bay, not the eagle cam.** Under `top2`, no seed case (true pair rank 2–3,
   54–77 km off). Under `comparable`, Oyster Bay with the filter on and its degraded copy both ways: the true pair
   first, refined 278 m from colsto's point, with a margin of 1.8–2.9 % over the second pair. The eagle cam isn't
   found under any rule or filter setting. The two Oyster Bay cases are one recording, so this is one recording found
   out of two.
3. **Pair rule: `comparable` becomes locate's default.** It finds one seed case with the filter off and two with it
   on, where `top2` finds none, and loses none. It costs six to ten times `top2`'s search time.
4. **Silence filter: on.** Under `comparable` it finds two seed cases where off finds one (Oyster Bay itself flips
   from an 87 km pair to the true pair), loses none, and the negatives stay unlocated. This reverses S4's default for
   `locate`; it rests on one recording, so the change is a PM decision for PLAN, recorded here as what the criterion
   says.

**What changes.** `locate` should default to `--pair-rule comparable` with the silence filter on (pending the PM, as
the default in PLAN S4 is the PM's). The eagle cam and the midnight case fail at the same step, the choice of the two
search events, which no rule over detect's top five fixes there; that is Phase 2 item 7's joint hypotheses, the next
work before step B. Two things the runs show that the plan doesn't yet use: a stated recording start time (the eagle
cam's stream metadata is good to 60 s) would reject every wrong clock seen here, and the winning margins (1.8–2.9 %)
are small enough that Phase 4's null threshold, not the margin, has to say whether a find is real.
