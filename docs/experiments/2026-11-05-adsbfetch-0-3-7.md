**Question.** The owner's `adsbfetch` (/Users/nsokolsky/projects2/adsb_data_fetcher) is at 0.3.7. I last tested 0.3.3.3 ([adsbfetch](2026-11-04-adsbfetch.md)). The changes since then that matter to us:

- the 3D `--near LAT,LON,ALTITUDE_M --radius-km`, and `--preserve-observations`;

The owner asked for three things to be validated first:
1. data correctness of 3D queries, exclusions, altitude references, and aircraft disappearing when networks combine;
2. cache and session reuse, naming every unnecessary request;
3. recent-data completeness, and whether `pending`, `partial` and `available` are accurate.

**Build tested.** `adsbfetch 0.3.7+179fe71a`: the editable install in the fetcher's checkout, which has no `.git`. Nothing was built or installed.

**Rules kept.**
- **Run the way the README's wrapper runs it.** Every call goes from the fetcher's checkout: its own `.env` loader, the automatic session, the default cache and the tool's default pacing (`--interval 5`). Calls are serial, one process at a time, because the throttle holds within one process only.
- **No cookie or token is ever read, copied or printed.** `.env`, the session file and the curl dumps are never opened, and no command line carries a cookie.
- **No changes to the tool or its cache.** No cache clear, no `--refresh` or `--no-cache`, no isolated cache folder, and the source left as found.
- **Public development sites only:** Oyster Bay, the eagle cam, Eclipse ESID 375, Essex (xc990819) and Livermore. Nothing from the Seattle home sessions.

## Criteria, fixed before the first fetch

**The queries.**
- **Four networks,** `adsbfi,airplaneslive,adsblol,adsbx`.
- **A recording-sized window:**
  - Oyster Bay 2026-09-08 20:45–21:15Z, with true flights a1dfeb at 20:53:00Z and ace391 at 21:08:41Z;
  - the eagle cam 2024-12-28 19:50–20:10Z, with a2baea at 19:58:28Z and a336e4 at 20:03:53Z;
  - ESID 375 2024-04-07 01:39:34Z for 30 min;
  - Essex 2025-04-20 04:10Z for 30 min.
- **A box about 30–40 km across** around each site.
- **The `--near` height is ellipsoidal,** as the README asks: DEM ground (`dopplertrack.terrain`), plus 1.5 m, plus an approximate EGM2008 undulation. That gives OB −30 m, eagle −22 m, ESID 375 250 m, Essex 103 m and Livermore 85 m. These undulations are good to a couple of metres, which matters nothing at a 4–10 km radius.
- **The driver** is [adsbfetch_0_3_7.sh](../../tools/experiments/2026-11-05/adsbfetch_0_3_7.sh).

**1. 3D correctness.**
- **The recomputation.** From each window's unfiltered output (`*_all`), I recompute every aircraft's minimum 3D distance to the `--near` point over its in-window positions. That uses WGS-84 ECEF, with `alt_geom` (GNSS, ellipsoidal) where present and `alt_baro` otherwise, as the README states.
- **The `--near R` output must hold exactly the aircraft with a minimum ≤ R.** Any aircraft whose minimum lies within the barometric slack of R is flagged as a boundary case, not a failure. The slack is the in-window difference between `alt_geom` and `alt_baro` across the box's aircraft.
- **The true flights.** At Oyster Bay and the eagle cam, both true flights are in the `--near 10` set, with their CPA positions.
- **No aircraft disappears when networks combine.** The union of the four single-network `--near 10` sets equals the four-network set, with no aircraft lost.
- **Each kept track holds an in-radius observation** after the two-second merge.
- **`--preserve-observations`** keeps every source's points, so its point count is at least the merged count, and it adds no aircraft.
- **`--props-only`** drops only aircraft whose type the registry says is a jet or helicopter. Unknown types stay.
- **Altitude reference.** In the output, `alt_geom` and `alt_baro` are never swapped. `alt_is_geom` agrees with which of them is non-null.

**2. Cache and session.**
- **The identical rerun** of a settled window (`*_again`) makes no network request for snapshots or traces, as the README says for settled history. Every request it does make is named from its manifest.
- **A smaller view of the same window** (`ob_shifted`) reuses the snapshots, as "one chunk serves every map area" says.
- **The session.** `auth status` showed the `.env` cookie selected and expired 6 h earlier, and a session file present.
  - The first uncached adsbx request must get a fresh session automatically and succeed.
  - The later calls reuse it: no renewals while more than 5 min remain.

**3. Recent data, at Livermore, today.**
- **Before the gate opens.** A window whose last half-hour closed less than 5 min ago exits 3, prints the retry time, writes `pending` to the metadata, and makes no source request.
- **Once eligible.** A window reports `partial` or `available` together with `next_check_at`. `available` must mean every requested snapshot was read and every selected track has positions in the window.
- **The rerun.** The same window run again after its `next_check_at` either keeps its result or improves it. An aircraft counted as missing earlier must not have been there after all.
